El estándar depende de la marca

Patinetes: diagnosticar antes de ofrecer la devolución. Packaging: rápido, exacto, 3 líneas. Un mismo párrafo puede ser excelente para una marca y pésimo para otra.

no todo error pesa igual

La gravedad importa

Un tono algo desviado molesta. Decirle al cliente algo incorrecto sobre su producto hace perder la cuenta. El modelo tiene que distinguir esos casos.

visión parcial

Nadie ve el panorama entero

Marta cubre 4 marcas y Nuria las otras 2. Un especialista pasó un mes cerrando tickets sin revisar el historial de pedidos y lo descubrió la marca.

La herramienta en una frase

Un lugar donde el team lead deja constancia de su juicio sobre respuestas ya enviadas y el especialista lo lee. Con el tiempo, esos juicios se convierten en tendencia (para el cliente) y en ejemplos (para el onboarding).

Qué no es

No es un helpdesk, ni un inbox, ni tickets, ni un producto de IA. Nada de scoring automático: si un modelo encaja, se describe en un párrafo en DECISIONS.md.

La decisión que leen primero

Qué lectura elegir: revisión, con la prueba y el coaching como consecuencias baratas

Sin reseñas guardadas no existen ni tendencia ni biblioteca. Ambas son consultas sobre la misma tabla. Por eso el núcleo es el bucle de revisión, y de las otras dos lecturas construimos solo la versión mínima que sale casi gratis.

construir bien

Revisión

Cola de respuestas de ayer → nota 1–5 → etiquetas de problema con gravedad → comentario. Rápido y consistente, con atajos de teclado. El especialista lo lee en "Mi feedback".

versión mínima

Prueba

Página de marca con la media semanal y los problemas más frecuentes. Es un GROUP BY sobre las reseñas. Sin exportación ni PDF.

Lo que dejamos fuera, y por qué

  • Login real: lo permiten simular y no aporta señal.
  • Importación del helpdesk: "ahora no". El modelo lo prepara con source + external_id.
  • Scoring con IA: explícitamente es lo equivocado.
  • Calibración entre leads, notificaciones, exportes: son V2.
  • Biblioteca de coaching: solo el flag en el modelo.

Supuestos que hay que escribir

  • Una reseña por respuesta y por revisor.
  • El tiempo de respuesta se calcula (sent_at − received_at), no se juzga.
  • Las etiquetas de problema son un catálogo global con gravedad. Las marcas no las personalizan en V1.
  • El especialista solo ve sus propias respuestas reseñadas, en todas sus marcas.
  • El lead ve todo lo de las marcas que lidera y nada de las demás.

Pesa 13 puntos · "¿podemos construir encima?"

Arquitectura recomendada: un monolito Next.js por capas, con Postgres como guardián final

Una sola app Next.js (App Router) que habla directo con Supabase. Sin backend aparte. La separación de responsabilidades la dan las capas dentro de la app, no los servicios.

Reglas de las capas

  • Lecturas en Server Components llamando a server/data. Nunca Supabase desde el navegador.
  • Escrituras con server actions: getCurrentUser() → zod.parse → requireLeadOf(brandId) → query.
  • brandId se deriva de la BD (la respuesta a la que pertenece), nunca del body del formulario.
  • Un único route handler JSON (/api/brands/[slug]/replies) para cumplir "si pedimos a la API otra marca, dice que no". Devuelve 403.
  • service_role solo en el script de seed. La app usa siempre el JWT del usuario, así que RLS aplica siempre.
  • Páginas con datos por usuario = dinámicas. Nada de unstable_cache o "use cache" sin el usuario en la clave.
  • Tipos generados con supabase gen types, así la BD es la fuente de verdad.
  • Agregados (tendencia, top problemas) como vistas SQL con security_invoker = on, para que respeten RLS.
AlternativaPor qué no ahora
Backend aparte (NestJS / Express)Duplica la autorización, un servicio más que levantar en el README y ~1 h que no hay. Supabase + RLS ya es la capa de datos segura. Sería razonable cuando llegue el importador o haya integraciones.
tRPC / React QueryLas server actions y los Server Components cubren lectura y escritura sin estado de cliente. Es menos código para revisar.
Turborepo + packages/*Todavía hay un solo consumidor. El workspace de pnpm basta, y packages/db aparece cuando exista apps/ingest.
Solo chequeos en Next (sin RLS)Un olvido en una query es una fuga. Con RLS, el olvido devuelve vacío en lugar de datos ajenos.
Solo RLS (sin chequeo en Next)Devuelve una lista vacía en lugar de "no". La UI no distingue "sin datos" de "sin permiso".
 
// apps/web/features/review/actions.ts
'use server'
export async function saveReview(input: unknown) {
  const user = await getCurrentUser();                  // 401 si no hay sesión
  const data = reviewSchema.parse(input);               // zod: score 1–5, issues[], comment
  const reply = await getReplyForReview(data.replyId);  // RLS: null si no la puede ver
  if (!reply) throw new NotFoundError();
  await requireLeadOf(user, reply.brandId);             // 403 explícito
  await insertReview({ ...data, brandId: reply.brandId, reviewerId: user.id });
  revalidatePath('/review');
}

Decisiones que defienden el modelo

  • Rol por marca (brand_memberships), no profiles.role. Un lead de 4 marcas no ve las otras 2.
  • unique(source, external_id): la futura importación hace upsert sin duplicar.
  • brand_id desnormalizado en reviews con FK compuesta (reply_id, brand_id) → replies(id, brand_id). RLS sin joins y sin poder mentir sobre la marca.
  • issue_types como tabla, no enum de Postgres. Añadir una categoría es un INSERT, no una migración. active en lugar de borrar.
  • Gravedad en el tipo de problema: "información incorrecta" es crítica y "tono" es menor.

Qué se rompe primero al crecer

  • Tendencias calculadas en vivo sobre miles de reseñas: vista materializada o rollup semanal.
  • Una sola nota 1–5 no captura criterios por marca: rúbrica versionada por marca (rubric_version).
  • Dos leads calificando lo mismo: hace falta calibración.
  • Índices: replies(brand_id, sent_at), replies(specialist_id), reviews(reply_id).

Dónde se aplica la autorización

Recomendación: defensa en profundidad. RLS en Postgres como garantía final y un chequeo explícito en el servidor de Next para devolver 403 (RLS por sí sola devuelve una lista vacía, y el enunciado pide que la API "diga que no").

recomendado

A · Usuarios de seed reales en Supabase Auth

El seed crea los usuarios en auth.users con contraseñas conocidas. El selector hace el login en el servidor. RLS usa auth.uid() de verdad. Auth real después = cambiar el selector por un formulario de login (o magic link/SSO). Las políticas no se tocan.

alternativa

B · Firmar el JWT en el servidor

Una cookie con el id elegido, y el servidor firma un JWT con el secreto del proyecto. Funciona, pero depende de la clave JWT legacy (las versiones nuevas de Supabase usan claves asimétricas) y es fácil de hacer mal. Úsala solo si A se complica.

-- Helper: evita recursión de RLS y centraliza la regla
create function public.is_lead_of(b uuid) returns boolean
language sql stable security definer set search_path = '' as $$
  select exists (select 1 from public.brand_memberships m
                 where m.user_id = auth.uid() and m.brand_id = b and m.role = 'lead');
$$;

alter table public.replies enable row level security;
create policy replies_read on public.replies for select to authenticated
  using (specialist_id = auth.uid() or public.is_lead_of(brand_id));

alter table public.reviews enable row level security;
create policy reviews_read on public.reviews for select to authenticated
  using (public.is_lead_of(brand_id)
         or exists (select 1 from public.replies r
                    where r.id = reply_id and r.specialist_id = auth.uid()));
create policy reviews_write on public.reviews for insert to authenticated
  with check (reviewer_id = auth.uid() and public.is_lead_of(brand_id));

Esqueleto de DECISIONS.md

Producto

  • Problema real: no hay registro del juicio de calidad, así que no hay coaching, ni prueba, ni alerta temprana.
  • Construí el bucle de revisión y lo cerré con la vista del especialista. La tendencia de marca, mínima.
  • Dónde encajaría un modelo: en elegir cuáles 5 leer. Marcar respuestas con riesgo (ofrece devolución sin pasos de diagnóstico en Voltra, no menciona el pedido). Condición: cientos de reseñas humanas para medir si su triage coincide con el de Marta. Nunca pone notas.
  • Preguntas V2: ¿la nota debe ser distinta por marca? ¿Quién mantiene las reglas de cada marca? ¿El cliente vería esto directamente?

Arquitectura

  • Server Components + server actions y una capa lib/data/* con acceso tipado.
  • Modelo: rol por marca, FK compuesta, source/external_id.
  • Authz: RLS y además requireMembership para devolver 403. Qué faltaría para auth real.
  • Qué se rompe primero al crecer.

IA

  • Cómo trabajaste: agente → PR → review.
  • 2 o 3 casos concretos en los que corregiste al agente (enlaza los comentarios del PR).
  • Un prompt del que estés orgulloso, pegado tal cual.

Estado

  • Terminado / a medias / sin tocar, en orden de prioridad.
  • Qué testearías primero: las políticas RLS con pgTAP o supabase test db, porque es donde un error cuesta una cuenta.
  • Lo que más criticarías si fuera el PR de otro, y por qué lo dejaste.

Para cada recorte, una frase de porqué. En la entrevista preguntan por dos cosas que recortaste.
